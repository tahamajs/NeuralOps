# Complete SVD Linear Attention Research Guide

This guide connects the whole documentation set into one research workflow. The repository is organized around a simple chain:

```text
question → architecture → implementation → verification → experiment → result → studio → deployment
```

Every Markdown family answers a different question in that chain. Use this page when moving between them so a theoretical claim does not become disconnected from code, measurements, or deployment behavior.

## 1. Start with the research question

Choose the constraint that matters most:

| Constraint | Primary material | Evidence to collect |
| --- | --- | --- |
| Long-context memory | [Attention catalog](./content/attentions/) and [attention deep dives](./content/attentions_blog/) | Sequence scaling, state size, masking behavior |
| Parameter or KV-cache cost | [Compression catalog](./content/compressions/) and [compression deep dives](./content/compressions_blog/) | Compression ratio, reconstruction error, memory footprint |
| Numerical stability | [Verification reports](./reports/) and [framework docs](./content/framework/) | Dtype behavior, finite outputs, gradient checks |
| Throughput and latency | [Benchmark reports](./reports/) and [results](./results/) | Device, batch, sequence length, precision, warm-up policy |
| Interpretability | [Visualization dashboard](./Attention_Visualization_Dashboard/Attention_Visualization_Dashboard.md) and [circuit tracer](./Mapping_Apply_the_Attention_Style_Interactive_Dashboard_to_ALL_Transformer_Components/CIRCUIT_TRACER.md) | Attention/state traces, intervention definition, reproducible inputs |
| Production operation | [Deployment guide](./DEPLOYMENT.md) and [Kaggle/GPU guide](./DEPLOYMENT.md) | Environment, worker topology, telemetry, rollback path |

## 2. Read an architecture specification correctly

Architecture Markdown files should be read in this order:

1. **Purpose and boundary** — what the module replaces or augments.
2. **Inputs and outputs** — tensor shapes, masks, cache/state contracts, and accepted dtypes.
3. **Algorithm** — the equations and recurrence that define the behavior.
4. **Complexity** — distinguish asymptotic complexity from measured latency.
5. **Failure modes** — padding, causal masking, rank selection, overflow, and unsupported layouts.
6. **Implementation reference** — map the documented name to its registry entry and source module.
7. **Evidence** — follow the verification or benchmark links before making performance claims.

The [attention modules](./content/attentions/) focus on sequence mixing. The [compression modules](./content/compressions/) focus on weights, activations, KV state, or token budgets. Hybrid systems may appear in both families; use the implementation path and catalog category as the authoritative distinction.

## 3. Move from Markdown to code

The framework is registry-driven. A new module should have:

- a stable implementation name under `Codes/framework/attentions/` or `Codes/framework/compression_engine/`;
- a registry/factory entry and an import path that works from a clean process;
- a Markdown specification under the matching `Docs/content/` family;
- shape, dtype, masking, and device behavior documented explicitly;
- focused tests for forward behavior, gradients, serialization, and edge cases;
- a catalog entry generated by `python generate_catalog.py`.

The [framework reference](./content/framework/) explains the shared registries, trainer, distributed execution, analysis, tracking, and result-saving layers. Read it alongside the module document rather than treating each architecture as an isolated implementation.

## 4. Verification is separate from benchmarking

Verification establishes correctness under a defined contract. Benchmarking measures trade-offs under a defined setup. A complete experiment records both.

At minimum, record:

```text
module + revision
model/backbone + task/dataset split
batch size + sequence length
device + GPU model + software versions
dtype + compilation/kernel settings
seed + warm-up/repetition policy
accuracy/F1/loss + latency/throughput + peak memory
```

Use the [verification reports](./reports/) for implementation confidence and the [results index](./results/README.md) for machine-readable evidence. Do not compare results from different sequence lengths, dtypes, or warm-up policies as if they were one leaderboard.

## 5. Interpret the result layer

The result files have different responsibilities:

- [`master_benchmark_summary.csv`](./results/master_benchmark_summary.csv) is convenient for tables and spreadsheets.
- [`master_benchmark_summary.json`](./results/master_benchmark_summary.json) preserves structured records.
- [`pareto_frontier.json`](./results/pareto_frontier.json) represents accuracy/efficiency trade-offs.
- [`all_histories.json`](./results/all_histories.json) feeds optional training plots in the Research Hub.
- [`master_empirical_benchmark_report.md`](./results/master_empirical_benchmark_report.md) explains the recorded snapshot in prose.

The UI displays telemetry as optional. “Offline” means the static site is functioning without a live experiment server; it is not a claim that a model failed. “Connected” means the configured server responded to the expected stats/history endpoints.

## 6. Use the studios as views over the same concepts

The studio specifications are not a separate product taxonomy. They are interactive views over the same framework concepts:

| Studio family | Related documentation |
| --- | --- |
| Attention canvas and math panel | Attention specifications and forward-pass verification |
| Compression studio | Compression specifications and benchmark results |
| KV cache monitor | Long-context attention and cache-compression reports |
| Weight matrix decomposer | SVD, low-rank, LoRA, and quantization documents |
| Training dynamics sandbox | Trainer, experiment logging, and history artifacts |
| Full pipeline studio | Guides, framework orchestration, and deployment docs |

When extending a studio, link its controls to a documented parameter and its output to a verifiable result. Avoid adding controls that have no implementation or evidence counterpart.

## 7. Deployment and contribution checklist

Before publishing a documentation or UI change:

```bash
python generate_catalog.py
git diff --exit-code -- Docs/catalog.json
node --check Docs/app.js
python -m json.tool Docs/catalog.json >/dev/null
```

Then verify that every new Markdown file has a top-level heading, all relative links resolve, and its catalog path exists. For experiment-facing changes, run the focused framework tests and record whether GPU execution was actually exercised.

The public Pages bundle is static. Configure telemetry with `window.FRAMEWORK_API_BASE`; never commit a private-network hostname or IP address. See [DEPLOYMENT.md](./DEPLOYMENT.md) for the complete Pages and server contract.
