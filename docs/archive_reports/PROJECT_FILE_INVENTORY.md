# NeuralOps File Inventory

This is the first static inventory for the repository. It records ownership and source-of-truth decisions discovered during the structure audit; it is not a generated benchmark result.

## Source-of-truth files

| Concern | Canonical location |
|---|---|
| Package metadata and tool configuration | `pyproject.toml` |
| Agent operating rules | `AGENTS.md` |
| Contributor conventions | `CONTRIBUTING.md` |
| Public project overview | `README.md` |
| Attention/compressor registry implementation | `neuralops/core/registry.py` |
| Static registry catalog | `neuralops/benchmarks/static_catalog.json` |
| CUDA/Triton execution policy | `AGENTS.md` and `.agents/skills/hpc-sharif-cluster/SKILL.md` |

## Root-level ownership

- `neuralops/`: importable production package.
- `scripts/`: command-line utilities, audits, benchmark launchers, and repository maintenance.
- `tests/`: automated verification grouped by subsystem and execution backend.
- `benchmarks/`: standalone benchmark inputs, configurations, and model assets.
- `examples/`: user-facing examples and recipes.
- `notebooks/`: exploratory and reproducible notebook workflows.
- `docs/`: extended documentation and historical technical material.
- `results/`, `logs/`, `audit/`, and similar directories: generated or experiment output; do not treat them as production source.

## Backend layering

The repository contains more than one kernel-facing directory, and they have different responsibilities:

```text
neuralops/layers or neuralops/attentions
  -> neuralops/core dispatch and registries
    -> neuralops/ops/cuda, neuralops/ops/triton, neuralops/ops/pytorch
      -> compiled/native, JIT, or reference execution

neuralops/core/cuda_kernels and neuralops/core/triton_kernels
  -> canonical kernel catalogs and core-level organization
```

Raw filesystem directory counts must not be presented as registry or implementation counts. The current canonical CUDA catalog is 110 unique modules / 114 native implementations; the raw `neuralops/ops/cuda/` directory count includes compatibility and support directories and is tracked separately.

## Test ownership

- `tests/benchmarks/`: benchmark integrity and contract regressions.
- `tests/gpu_exhaustive/`: remote GPU matrix validation.
- `tests/cuda_kernels/` and `tests/cuda_parity/`: native CUDA behavior and parity.
- `tests/triton_parity/`: Triton/reference numerical parity.
- Other `tests/<subsystem>/` directories own the corresponding production package.

## Audit status

- Initial repository-wide inventory (tracked files): **13,318 files**.
- Worktree source/document inventory excluding Python bytecode and `__pycache__`: **2,961 files** visible to `rg --files`.
- Dominant tracked extensions: **2,220 Python**, **268 JSON**, **138 CUDA `.cu`**, **135 C/C++ `.cpp`**, **70 JavaScript**, and **51 Markdown** files.
- The package tree contains **378 `__init__.py` package markers**; this is a package-structure measure, not a public API count.
- The test tree contains **24 named subsystem directories** with Python tests, including benchmark, CUDA, Triton, exhaustive GPU, validation, serving, surgery, and integration groups.
- The script tree contains **69 tracked utility and execution files**, including PBS launchers, benchmark entry points, audits, monitoring tools, and environment helpers.
- The local `.venv/`, cache directories, and generated bytecode are environment artifacts and are excluded from production structure decisions.
- Directory and top-level package inventory: complete for the initial audit.
- Registry and entry-point locations: identified.
- File-by-file caller graph: in progress.
- Duplicate/dead-file decisions: not made until imports, exports, registries, tests, scripts, and documentation references are cross-checked.

## Cross-reference findings

- `neuralops.attentions` is referenced by many tests and package metadata, so it cannot be treated as an unused mirror without a symbol-level compatibility audit.
- `neuralops.compression_engine` is referenced by tests and package metadata, so it is an active compatibility/API surface until proven otherwise.
- `neuralops.kernels`, `neuralops.core.cuda_kernels`, and `neuralops.ops.cuda` are all referenced by tests, public APIs, and benchmark code; none is a safe deletion candidate.
- Dynamic import mechanisms are present in `neuralops/__init__.py`, `neuralops/_lazy.py`, `neuralops/export/`, `neuralops/experiment_logging/`, and test utilities. Static absence of a direct import is not proof of dead code.
